# 通用开发工作流

这份文档是当前 Claude Code 适配包的主工作流说明。

它面向真实项目维护场景，而不是一次性代码生成。目标是让代理更像一个谨慎的实现协作者：先理解上下文，再遵守仓库习惯，做受控修改，并留下能帮助后续维护者接手的交付说明。

## 严格触发条件

当用户任务明显属于“要动代码”的场景时，必须严格执行这套工作流，尤其是出现下面这些意图时：

- 修改
- 实现
- 修复
- 重构
- 添加功能
- 调整现有行为
- 优化现有代码

如果用户是英文表达，也要把下面这些关键词视为严格触发条件：

- modify
- implement
- fix
- refactor
- add feature
- change behavior
- optimize existing code

## 核心原则

1. 改代码前先读取最相关的项目上下文。
2. 优先遵循项目已有习惯，而不是个人偏好。
3. 优先做最小、可控修改，不做大范围顺手重构。
4. 注释、日志、测试和文档要对齐现有代码仓库风格。
5. 验证和交付说明本身也是实现工作的一部分。

## 这套工作流主要在防什么

很多开发任务失控，并不是因为代码本身特别难，而是因为实现过程开始变得随意。常见问题包括：

- 还没读任务上下文就开始改代码
- 为了解一个局部问题顺手做了大范围重构
- 注释语言和当前模块的既有风格不一致
- 随手加日志，但和项目原有排查方式完全脱节
- 用户没要求却擅自改文档
- 交付时不说明假设、风险和验证缺口

这份工作流的目的，就是把这些高频问题变成默认要规避的边界。

## 必须遵循的工作流

### 1. 先识别项目根目录

优先根据用户给出的路径或仓库标识判断，例如：

- `.git/`
- `README.md`
- `package.json`
- `pyproject.toml`
- `Cargo.toml`
- `go.mod`
- `pom.xml`
- `build.gradle`
- 其他语言或框架的根目录标识

项目根目录之所以重要，是因为文档位置、配置文件、测试入口、脚本路径和备份规则通常都依赖它。

### 2. 先读取最相关的上下文

改代码前，先读取最能界定任务边界和当前实现状态的材料。

优先级如下：

1. 与当前任务匹配的 `*-开发文档.md`、`*-development-doc.md`、设计说明、ADR、任务说明、需求文档
2. 当前要修改的文件，以及相邻实现文件
3. 仓库级说明，例如 `README.md`、架构说明、配置文件、测试代码
4. 能说明当前行为的错误日志、快照、fixture、输入输出样例

如果存在与当前任务明确匹配的开发文档，必须先读再改。

如果多个文档都可能相关，而且会明显影响实现方向，需要先确认再动手。

如果没有任务文档，也不能跳过理解过程，要通过现有代码、测试和仓库说明建立上下文。

### 3. 提取当前实现上下文

至少要搞清楚：

- 当前行为是什么
- 已实现范围到哪里
- 已确认的业务或技术规则是什么
- 期望最终状态是什么
- 已知风险、测试缺口和待处理项有哪些

### 4. 保守修改

- 先读懂现有逻辑再动手
- 优先做最小、可控修改
- 保持当前项目风格
- 不做与当前任务无关的重构
- 不删除无关逻辑、注释、测试、配置、fixture 或用户已有改动

如果真正合理的修复必须扩大范围，也应该先明确知道自己为什么要扩大，而不是默默把任务做大。

## 注释规则

注释语言和注释风格必须跟随当前项目中最强的本地信号。

判断顺序如下：

- 用户明确要求优先
- 否则跟随当前被修改文件中的主注释语言
- 再看同模块相邻文件中的主注释语言
- 再看任务文档或技术说明中的主语言
- 再看仓库整体最稳定的注释习惯
- 如果仍然没有信号，默认英文

注释重点应放在意图、限制条件、边界处理、副作用、状态流转和不直观行为上。

不要给明显赋值、直接返回或简单包裹调用补低价值注释，除非项目原本就明确要求这样写。

## 日志与调试规则

如果需要新增日志或调试输出：

- 跟随项目现有日志体系和写法
- 只在关键检查点加
- 优先记录有助于排查的问题上下文、分支选择、参数准备、状态变化、副作用、失败原因和重试信息
- 避免在同一段逻辑前后写重复含义的日志
- 不要无缘无故把原本安静的链路变成高噪音输出

日志的价值应该是帮助定位问题，而不是单纯证明某一行被执行到了。

## 验证规则

验证不是可有可无的收尾动作，而是任务的一部分。

能做验证时，尽量：

- 跑当前改动附近最相关的现有测试
- 先做局部、聚焦的验证，再考虑更大范围检查
- 优先使用项目原生已有的测试和校验方式
- 交付时说明验证了什么、没验证什么

如果没法验证，也必须明确写清：

- 为什么没法验证
- 当前最大残留风险是什么

## 文档维护规则

只有用户明确要求时，才允许更新开发文档或技术说明。

如果需要更新：

1. 先写高层结构。
2. 只聚焦核心文件、模块、类或函数。
3. 同时写运行流程和方法调用链路。
4. 方法调用链路中的每一行都要写明入参、出参和作用。

文档类任务应优先结合 `references/` 下的模板和写作说明，而不是临时拼凑一份空泛总结。

## 备份与高风险操作

如果用户明确要求备份，则默认按规则备份到项目根目录 `backups/` 文件夹，并且同源文件最多保留三份备份。

如果项目本身已经有既定备份目录，或者用户明确要求其他目录名，则优先跟随项目或用户要求。

对部署命令、破坏性环境操作或不可逆动作保持谨慎，除非用户明确要求且目标平台允许执行。

## 交付说明

任务完成时需要说明：

- 读取了哪些文档或上下文
- 修改了哪些文件、模块、类或函数
- 注释最终用了什么语言，以及为什么
- 如果新增了日志或调试输出，加在了哪里
- 文档是否刻意保持未修改
- 是否做了验证；如果没验证，原因是什么

## 期望结果

如果这套工作流被正确执行，最终效果应该像一次认真负责的仓库维护：

- 改动是容易理解的
- 范围是受控的
- 风格是贴合项目的
- 文档说明是清楚的
- 后续维护者不会只能靠 diff 去猜你的意图
