# 注释语言策略

当任务涉及新增或修改代码注释、配置注释、脚本注释、测试注释或技术文档说明时，读取本说明。

## 核心原则

注释语言要跟随项目上下文，而不是跟随个人习惯。

目标是让当前维护这套代码的人读起来最自然、最一致，而不是为了形式统一去强行套模板。

## 决策顺序

按以下顺序判断注释该用什么语言：

1. 用户明确要求
2. 当前被修改文件里已经存在的注释语言
3. 同模块相邻文件中的主注释语言
4. 当前任务开发文档、README、ADR、设计说明里的主语言
5. 仓库整体最稳定、最常见的注释语言
6. 如果没有明确信号，默认使用英文

## 实际规则

- 如果当前模块本来就是英文注释为主，就继续写英文注释。
- 如果当前模块和任务文档都是中文为主，就继续写中文注释。
- 如果仓库整体是双语，但你正在修改的包或目录明显是英文优先，就按英文走。
- 如果项目几乎没有注释，不要主动发明中英双语注释风格，除非用户明确要求。

## 作用范围

- 优先按“当前模块”判断，不一定按整个 monorepo 一刀切。
- 优先服从离改动点最近、最稳定的既有习惯。
- 同一段新增或修改的代码，注释语言尽量保持单一，除非项目本来就有明确混用规范。

## 质量要求

- 只在确实能帮助理解的地方写注释。
- 优先解释意图、限制条件、边界处理、状态流转、副作用和不直观行为。
- 不要给明显赋值、直接返回、简单调用写低价值注释。
- 注释里的业务术语要跟现有项目表达保持一致。

## 信号冲突时

如果多个信号冲突，而且会明显影响维护一致性：

- 先跟随当前被修改文件里的既有风格
- 如果当前文件不明显，再跟随当前任务文档对应模块的语言
- 如果仍然不明确，在交付说明里写清采用了什么假设
