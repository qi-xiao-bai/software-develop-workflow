# 开发文档模板

在用户明确要求维护开发文档时，按这个模板更新项目根目录下对应的 `*-开发文档.md`、`*-development-doc.md` 或其他任务说明文档。

这是一份“当前代码实现说明”风格的公共模板，重点是把当前代码实际怎么实现、实际怎么运行讲清楚，不写方案汇报，不写未来规划，不绑定具体语言或框架。

## 必须保留的核心标题

下面这些标题是固定骨架，必须保留：

```md
# XXX - 当前代码实现说明

## 功能目标

## 文档目的

## 代码分层与职责

## 核心类与职责

## 关键方法说明

## 关键对象、字段、状态

## 完整流程链

## 当前实现特征与限制

## 边界处理与特殊说明

## 维护、风险与后续改进

### 维护与扩展建议

### 当前问题与优化方向

### 异常与错误处理

### 后续待补工作

### 风险与注意事项

## 总结
```

## 每个核心标题下面应该写什么

### 功能目标

说明当前功能要解决什么问题、达到什么结果。

这里不要一上来堆实现细节，而是先把“为什么有这个功能”讲清楚。

### 文档目的

说明这份文档覆盖的范围，以及阅读者读完后应该能理解什么。

至少要回答：

- 这份文档描述的是哪一块实现
- 看完后能掌握哪些关键内容

### 代码分层与职责

先把整体结构讲清楚。

如果当前实现有明显层次，例如：

- Controller / Entry
- Service
- Repository / DAO
- Domain / Model
- Support / Utility
- Async / Job / Queue

这一节就要写清每一层负责什么、不负责什么。

### 核心类与职责

这里只写真正影响主链路理解的核心类，不要把所有类都堆进来。

每个核心类至少写清：

- 它负责什么
- 它依赖什么
- 它在整体流程里处于什么位置

### 关键方法说明

这里只写核心方法，不需要把所有 helper 都展开。

每个关键方法尽量写清：

- 入参
- 出参
- 作用
- 调用时机
- 重要副作用

### 关键对象、字段、状态

这里写真正驱动流程的对象和状态，例如：

- 请求对象
- 响应对象
- 领域对象
- 数据表
- 状态字段
- 枚举值
- 消息体

要说明这些对象、字段或状态为什么关键，以及它们在流程中起什么作用。

### 完整流程链

这一节先用自然语言把整个流程讲清楚。

它更偏“业务和实现结合的整体说明”，重点是让人先看懂大图，而不是一上来就陷入方法级细节。

### 当前实现特征与限制

这里要诚实说明当前实现的特征和限制，例如：

- 当前是同步实现，不是异步实现
- 当前实现偏可读性，不偏极致性能
- 仍有硬编码假设
- 某些模块耦合较高
- 某些分支还是过渡方案

### 边界处理与特殊说明

这里写容易被忽略的特殊分支、业务例外、非默认路径和边界处理逻辑。

如果一个功能除了主流程之外还有特殊规则，这一节必须写清楚。

### 维护、风险与后续改进

这一节作为一个合并大节使用，统一承接维护建议、当前问题、错误处理、待补工作和风险说明。

这一节下面固定拆成下面 5 个小标题：

#### 维护与扩展建议

告诉后续维护者：

- 新逻辑适合加在哪里
- 哪些地方不要随便动
- 哪些约束必须保持
- 扩展时容易踩什么坑

#### 当前问题与优化方向

把当前已经知道的问题、薄弱点和优化方向写出来。

不要停留在“后续可优化”“耦合偏高”这种空话上。

尽量具体，例如：

- 哪个方法过长
- 哪段逻辑重复
- 哪块耦合偏高
- 哪类异常处理不够完整

#### 异常与错误处理

这里要说明：

- 异常在哪里捕获
- 哪些错误直接抛出
- 哪些错误会转成业务提示
- 哪些失败会重试、降级或终止
- 当前错误日志是否足够

#### 后续待补工作

这里写明确已经知道但还没完成的内容。

它和“当前问题”不同：

- 当前问题偏当前缺陷和不足
- 后续待补工作偏明确还没做完的工作

尽量直接列出具体没补完的内容，例如：

- 哪个分支还没支持
- 哪个重试还没补
- 哪个校验还没做
- 哪个兜底还没接上
- 哪个配置清理还没完成

#### 风险与注意事项

这里写后续维护时最容易出问题的点，例如：

- 性能风险
- 并发风险
- 状态流转风险
- 外部依赖不稳定
- 配置依赖强
- 临时兼容逻辑容易误删

### 总结

最后用几句话收住全文，强调：

- 当前实现处于什么状态
- 主链路是什么
- 主要风险是什么
- 后续维护最该注意什么

## 条件必选标题

下面这些标题不是每份文档都必须出现，但在满足条件时必须补上：

- `## 方法调用链路`
  特定功能开发文档应当写；整项目总览文档可以不写。
- `## 当前完成情况`
  当文档必须明确说明已完成范围、部分完成范围、未完成范围或现有验证情况时再写。

### 方法调用链路

这一节在需要时必须写细。

每条关键链路尽量写清：

- 入参
- 出参
- 作用

如果调用链比较长，建议先写一段“整体链路概述”，再逐步往下列。

### 当前完成情况

这一节只写真实现状，不写空泛总结。

建议写清：

- 主流程是否已经完成
- 哪些场景已支持
- 哪些场景仍不完整
- 当前测试覆盖到了哪里

## 扩展标题

下面这些标题不是必须项，只有当前功能确实需要时再补充：

- 仓库入口与关键路径
- 依赖、配置与外部交互
- 验证与测试现状
- 排查与调试说明
- 关键接口或消息体说明
- 状态流转补充说明

扩展标题的作用是补充复杂度，不是替代核心骨架，也不能替代上面的条件必选标题。

## 方法调用链路示例

```md
## 方法调用链路

整体链路概述：
请求从入口层进入，进入主服务或核心模块完成编排，处理中间状态或持久化，再执行后置逻辑，最后返回结果。

请求进入系统
-> `ApiHandler.handle(request)`
   - 入参：`request`
   - 出参：`Response`
   - 作用：接收入口请求并触发主流程
-> `TaskService.execute(command)`
   - 入参：`command`
   - 出参：`TaskResult`
   - 作用：执行业务主链路并汇总结果
-> `TaskService.buildContext(command)`
   - 入参：`command`
   - 出参：`Context`
   - 作用：构建执行上下文和前置数据
-> `Repository.save(context.state)`
   - 入参：`context.state`
   - 出参：持久化结果或无直接返回
   - 作用：保存当前状态
-> `Notifier.publish(context)`
   - 入参：`context`
   - 出参：无返回或后置处理结果
   - 作用：执行通知、异步任务或后处理逻辑
-> 返回 `Response`
   - 作用：将最终结果返回给调用方
```
